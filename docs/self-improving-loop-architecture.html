Executive Summary & Core Thesis

As IntoChat launches v0.24.0 alongside cloud v0.2.0, we possess all atomic primitives for autonomous software development: durable flow execution (EngineerFlow), black-box candidate verification (ProcessCandidateHost, EngineerLiveVerifier), multi-model local/frontier routing (PR #390), out-of-process sandboxing (IntoChat.OS.Sandbox), and device hardware/model tracking (Devices module).

The Breakthrough: Rather than offloading coding execution to expensive cloud VMs or third-party proprietary sandboxes, IntoChat will turn the user's enrolled client devices (Windows, Linux, Android) into sovereign compute and sandbox execution nodes. Connected clients execute code to orchestrate Neurons over closed edge reverse proxies, leveraging local GPUs (Ollama/Foundry) and local CPU cores, with seamless fallbacks to lightweight OS containment (Microsoft MXC), leased devcontainer slots (agent-dev-slots) for heavy Aspire runs, and headless Azure Container Apps Dynamic Sessions when user machines are asleep.

Gap 1: Device Task Relay Network

The Devices module today relays chat completions (IDeviceChatRoute) but does not expose a general IComputeExecutionRoute for shipping git worktrees, executing build commands, or streaming stdout/stderr back to the brain.

Gap 2: Build SDK in Sandbox Sandbox

IntoChat.OS.Sandbox uses an in-memory AppLoadContext that bans process spawning. To run dotnet build or git, we need OS-level containment (JobObjects/cgroups via MXC or leased devcontainer slots) rather than in-process assembly isolation.

Gap 3: Multi-Agent Squad Chat Orchestration

While Ino and individual agents run inside the kernel, IntoChat OS lacks a first-class "Squad Circle" UI where users can watch Planner, Coder, Verifier, and Security Lead converse, debate diffs, and stream logs in real time.

End-to-End Live Loop: Discussion → Verification → Promotion

How a user request in chat traverses Ino, dynamic agent squads, compute dispatch to connected clients, isolated candidate verification, and human-in-the-loop promotion.

Figure 1: Full 5-Stage Lifecycle of IntoChat Autonomous Self-Improving Loop
1. Discussion → Spec Conversion Intent

A user or squad member requests a feature, optimization, or bugfix in IntoChat. Ino's conversational intelligence extracts unambiguous acceptance criteria, affected architectural boundaries, and non-goals, minting an IssueSpec and binding to a tracked GitHub issue.

2. Squad & Synapse Orchestration Planning

Ino convenes a specialized dynamic squad inside IntoChat OS: Lead Planner, Refactor Scout (running CodeGraph/LSP queries), Coder, and Security QA. The plan is partitioned into small vertical slices (≤ 150 LOC) with strict Old Code → New Code definitions.

3. Sovereign Compute Dispatch Execution

The Devices module matches tasks against active paired nodes. Code generation defaults to local Ollama (zero API cost), automatically escalating to frontier reasoning models (Claude/Codex) via PR #390 only when two local repair cycles fail.

4. Isolated Candidate Verification Verification

ProcessCandidateHost builds the candidate branch in an isolated git worktree and boots a headless OS instance on an ephemeral loopback port (never 5080/5081) with a temporary home (never ~/.intochat). EngineerLiveVerifier tests /health, MCP endpoints, and telemetry before presenting the result.

💻 Option A: IntoChat Native Sandbox + Connected Client Nodes Owner Favorite

Leverages the user's paired IntoChat client installations (Windows, Linux, or Android) as compute nodes. When connected, the client registers its hardware capabilities (CPU/GPU/RAM via HardwareProbe) and local models (via ILocalRuntime). The central brain dispatches coding tasks to the client over the secure P-256 paired device edge.

Advantages
  • Zero Cloud Infrastructure Bills: Runs 100% on hardware the user already owns.
  • Native Neuron Orchestration: Sandboxed code calls directly into brain Neurons via IntoChatClient.
  • Data Privacy & Custody: Source code and secrets never leave the user's trusted devices.
  • Android Edge Nodes: Android devices can contribute local small-model drafting (Qwen 1.5B) or run lightweight verification.
Limitations
  • Offline Sensitivity: Jobs cannot run if the user's client devices are offline.
  • Sandboxed SDK: The native C# sandbox load context prohibits process spawning, requiring a helper runner for dotnet build.
🛡 Option B: Microsoft Execution Containers (MXC / Microsoft.Mxc.Sdk) Desktop Native

Microsoft's official open-source policy-driven containment SDK (Microsoft.Mxc.Sdk for .NET). Uses Windows ProcessContainer (job objects + AppContainer tokens + Learning Mode) and Linux cgroups/namespaces to confine processes without needing Docker Desktop or full hypervisor VMs.

Advantages
  • First-Class .NET SDK: Clean C# bindings directly consumable by IntoChat.OS.Host.
  • Sub-Second Startup: Boots an isolated process container in < 150ms.
  • No Docker Dependency: Runs out of the box on Windows and Linux workstations.
  • Granular Resource Policies: Limits readable directories, network domains, and scrubbed env vars.
Limitations
  • macOS Support: MXC on macOS is experimental / less mature than Windows.
  • Single-Host: Designed for local process containment, not multi-node orchestration.
📦 Option C: Leased Devcontainer Slots (hanzhad/agent-dev-slots + Aspire) Aspire Gold Standard

Adopts the proven agent-dev-slots pattern: pre-warmed, leased Docker Compose devcontainer slots (acquire / run / release). Operates as unprivileged uid 1000, with ephemeral homes (no ~/.ssh leaks), dynamic port leasing, and full support for running .NET Aspire multi-service systems in isolation.

Advantages
  • Full Aspire Stacks: Can boot full Postgres, Redis, Orleans, and Web nodes without port clashes.
  • Zero Collision Across Agents: Leased slots guarantee parallel agents never step on files or ports.
  • Credential Scrubbing: Injects temporary tokens (e.g. FORGE_AUTH) without persisting keys.
  • Reproducible CI Match: Uses exact same container image as GitHub Actions CI.
Limitations
  • Requires Docker: Host must have Docker or Podman engine running.
  • Higher Memory Footprint: Pre-warmed slots consume RAM continuously.
☁ Option D: Cloud Ephemeral Containers (ACA Dynamic Sessions) vs. Codespaces Headless Fallback

Cloud-hosted scale-to-zero sandboxes. Azure Container Apps (ACA) Dynamic Sessions provides lightweight Kata microVMs allocated on demand via REST. GitHub Codespaces provides full-featured hosted developer environments suitable for external open-source contributors.

Advantages
  • Always Available: Operates when the user's PC is powered off or disconnected.
  • Hypervisor Isolation: Kata microVMs offer hardware-level security boundaries.
  • Elastic Bursting: Run 10 parallel candidate tournaments simultaneously.
Limitations
  • Metered Cloud Cost: Incurs ongoing cloud billing per compute minute.
  • Slower Cold Start: MicroVM allocation takes 5–15 seconds.
  • Closed Gateway Latency: Neuron edge calls incur network roundtrip delays.
Section 4

Recommended Target Architecture: Unified Sovereign Hybrid

How these four technologies compose cleanly into an elegant, tiered architecture instead of competing with each other.

The 5-Tier Hybrid Execution Framework Unified Synthesis

Rather than choosing one execution engine, we establish a clean division of responsibility: IntoChat Sandbox + Connected Client Nodes forms the sovereign control and routing plane, with containment backends selected dynamically based on task weight and environment:

Tier 1: Desktop OS Containment (MXC)
On developer PCs and enrolled client workstations (Windows/Linux), IntoChat.OS.Sandbox adopts Microsoft.Mxc.Sdk. Confines coding agents to target worktrees with sub-second startup, zero Docker overhead, and scrubbed environment variables.
Tier 2: Candidate Verification (agent-dev-slots)
For heavy candidate verification requiring live Aspire multi-service orchestration (Postgres, ClickHouse, Redis, Orleans silos), ICandidateHost leases an isolated slot from agent-dev-slots with dynamic port mapping and unprivileged UID 1000.
Tier 3: Headless Cloud Fallback (ACA Sessions)
When the user is away and all paired client machines are asleep, the Cloud Control Plane transparently routes background refactoring and PR triage to Azure Container Apps Dynamic Sessions (Kata microVMs) scaling to zero when idle.
Tier 4: Mobile & Edge Coprocessors (Android)
Enrolled Android clients running FlutterMix contribute local small-model drafting (e.g. Qwen 2.5 Coder 1.5B via ONNX/llama.cpp) or experimental Linux-on-Android terminal environments for lightweight triage and test streaming.
Hard Invariant: The Zero-Trust Sandbox Boundary

Across all four tiers, three non-negotiable security invariants are enforced:
1. Closed Orleans Gateway: Sandboxed processes and client nodes never join the Orleans cluster. They communicate exclusively through the authenticated reverse-proxy edge (SandboxEdgeEndpoints) using short-lived AppToken credentials bound to brain and app.
2. Zero-Token Vault: Frontier API keys (Claude, OpenAI) and Git credentials live sealed in the Host Vault. They are injected as ephemeral headers during proxy transit and never written to the candidate filesystem or sandbox environment.
3. Mandatory Human ChangeCard Gate: No candidate branch can be merged to master or pushed to an external origin without explicit human sign-off via an interactive ChangeCard in IntoChat UI.

Phased Rollout Plan & Owner Decisions

Structured vertical slices for implementation, accompanied by the interactive decision panel for owner sign-off.

Slice RFC-1: Connected Client Compute in Devices Slice 1

Extend IntoChat.OS.Modules.Devices to advertise compute capacity (CPU, GPU, RAM, SDK presence) alongside existing local models. Implement IComputeExecutionRoute over the paired P-256 edge relay, enabling the brain to dispatch git worktrees and stream execution progress.

Slice RFC-2: MXC Desktop Containment Backend Slice 2

Integrate Microsoft.Mxc.Sdk into IntoChat.OS.Host. Implement MxcSandboxHost providing sub-second OS-level process containment on Windows (ProcessContainer) and Linux (cgroups), replacing raw JobObjects with policy-driven folder and network isolation.

Slice RFC-3: Leased Devcontainer Slot Provider Slice 3

Implement AgentDevSlotsCandidateHost implementing ICandidateHost. Allows heavy candidate verification runs to lease pre-warmed Docker Compose slots with dynamic port allocation and unprivileged UID 1000 execution for complete Aspire full-stack fidelity.

Slice RFC-4: Cloud ACA Sessions & Android Edge Worker Slice 4

Deliver the headless cloud fallback via Azure Container Apps Dynamic Sessions for off-hours autonomous improvements, plus the Android client background worker for local small-model drafting and test output streaming.
