# Architecture

IntoChat is built on DigitalBrain, the framework in [`framework/`](../framework/README.md). The framework defines neuron, signal, synapse, app and module; see the [framework docs](../framework/docs/README.md). This page describes the product on top of it.

The product has four parts.

| Part | What it is | Where it lives |
| --- | --- | --- |
| Kernel | The host process: it composes the modules, hosts the neurons and serves the shell. | `src/IntoChat.OS.Kernel`, `src/IntoChat.OS.Sandbox` |
| System apps | The apps compiled into the product. | `src/IntoChat.OS.Apps` |
| Modules | Capabilities and connectors the kernel composes. | `src/Modules` |
| Shell | What you see: the Flutter client and the desktop launcher. | `ui`, `src/IntoChat.OS.Desktop` |

`src/IntoChat.OS.Host` (`IntoChat.OS.Host`) is the OS host layer that every OS process and module stands on: service defaults, configuration names (`IntoChatOSNames`), logging, confined process execution, cluster contracts, the Orleans client, the kernel's module and type ports (`OsModule`, `IKernel`, `CompiledTypes`) and the OS primitives (`AppRef`, `ConversationId`). It references no module and not the kernel. `src/Modules/Identity` (`IntoChat.OS.Modules.Identity`) is the identity module: accounts, sessions, grants, the vault, connections and integrations, with `SiloAccessCallFilter` as the call enforcement point. Other projects use its contracts in `src/Modules/Identity/Contracts` (`IntoChat.OS.Modules.Identity.Contracts`). The kernel's own platform pieces (`NeuronsGrpcService`, brain store custody, operator diagnostics) are in `src/IntoChat.OS.Kernel/Platform`. `src/IntoChat.OS.AppHost` (`IntoChat.OS.Aspire.Hosting`) provides .NET Aspire helpers (`AddIntoChatOSBrain` and `AddIntoChatOSContainer` in `Hosting/IntoChatOSHostingExtensions.cs`, `AddIntoChatOS` and `AddKernel` in `Hosting/Composition/OperatingSystemHosting.cs`, and the fluent deployment chain `DeploymentChain` / `AIDeployment` used by `src/IntoChat.OS.AppHost/AppHost.cs`). A component's own hosting code lives in its `Hosting` folder (`src/Components/Aspire/Hosting/AspireModuleHosting.cs`, namespace `IntoChat.Aspire.Hosting`) and is compiled only into the AppHost by a linked `Compile` item; the component's project removes `Hosting/**` from its own compile items and the AppHost includes it (`ComponentFacts`). `src/IntoChat.OS.Contracts/Shell` (`IntoChat.OS.Contracts`) holds the shell wire contracts and signals separately from `src/Modules/Workspace/Shell` (`IntoChat.OS.Modules.Workspace`).

## AppHost resource names

`src/IntoChat.OS.AppHost/Hosting/Composition/ResourceNames.cs` (`ResourceNames`) names the root, the component nodes, their renamed children and the kernel; a few run-mode resources still carry the `Modules-` prefix and are listed in `OWED.md`, and the data-bearing and parameter names stay frozen. The new names apply to local runs only; a published deployment keeps the names it had, because renaming a deployed resource creates a second one beside it (`ResourceNames.Pick` is the single switch).

| Resource | Local run | Publish |
|---|---|---|
| root | `intochat` | `Modules` |
| component node | its shown name: `ai`, `aspire`, `devices`, `github`, `mcp`, `orleans`, `sandbox`, `shell` (module id `flutter`), `web` (module id `webtools`) | `Modules-<id>` |
| local model runtime | `ai-ollama`, with Aspire's own companion `ai-ollama-openwebui` | `Modules-ollama` |
| web search | `web-searxng` | `Modules-searxng` |
| sandbox worker | `sandbox-worker` | `sandbox` |
| shell app | `shell-desktop` (`shell-web` for the web target) | `FlutterShell` |
| shell device targets | `shell-android`, `shell-linux` (run only; `flutter-android`, `flutter-linux-wsl` before the rename) | not present |
| kernel | `os` (`os-a`, `os-b` for several instances) | `OperatingSystem-a` |
| gateway | `os-gateway` | `OperatingSystem-front` |
| rebuild helper | `os-rebuilder`, generated by Aspire | not present |

Data volumes, parameter resources and the frozen names `Modules-grainstate`, `Modules-clustering`, `Modules-storage`, `Modules-intochat-os-master-key` and `Modules-searxng-secret` keep their `Modules-` names in both modes. At run time the kernel recognises `os` and the legacy `OperatingSystem` role (`KernelNames` in `src/Components/Aspire/KernelNames.cs`).

## Kernel

`src/IntoChat.OS.Kernel/Program.cs` builds a standard `WebApplicationBuilder` using `AddIntoChatOSKernel`, `MapIntoChatOSKernel`, and `RunIntoChatOSKernelAsync` in `src/IntoChat.OS.Kernel/KernelHost.cs` (which also accepts `rootAssembly`, `configureServer`, `beforeAccountSession`, `configureApp`, and `cancellationToken` so external hosts can compose additional modules and hooks):

1. When `AzureInstaller.IsInstall(args)` matches, it discovers modules with `OperatingSystemModules.Discover(rootAssembly)` and runs `AzureInstaller.Run` before exiting.
2. Otherwise it applies `LocalRunDefaults.Apply`, reads `IntoChatOS:Topology` (`IntoChatOSNames.TopologyKey`), and discovers modules via `OperatingSystemModules.WithWindowsEdge(rootAssembly)` on Windows or `OperatingSystemModules.Discover(rootAssembly)` elsewhere, keeping only those where `module.LoadsUnder(topology)` is true.
3. `builder.AddIntoChatOSServer` configures the Orleans silo, the DigitalBrain runtime, `server.AddOperatingSystem(catalog)` (modules and shipped OS apps), and any `configureServer` callback (enabling the Orleans dashboard when configured); `builder.Services.AddIntoChatOSMcp()` registers MCP services.
4. `app.MapIntoChatOSServer(beforeAccountSession)` maps the static web shell, HTTP endpoints, health probes, and gRPC endpoints; `app.MapIntoChatOSMcp()` maps `/mcp` plus the brain-scoped `/brains/{brainId}/mcp` route (via `BrainRouteGroups.Brain` with `GuestSurface.Door`).

The `IntoChatOS:Topology` setting picks clustering, state stores, streams, reminders and secrets.

The sandbox worker in `src/IntoChat.OS.Sandbox` runs app code made at run time outside the kernel process. See [sandbox and live behaviors](sandbox-and-live-behaviors.md).

## System apps

Each system app has a folder in `src/IntoChat.OS.Apps`, for example `Ino`, `Creator`, `Desktop`, `Settings` and `Tasks`. A system app is a neuron. `InoApp` and `CreatorApp` derive from the framework's `Screen<TState>`: the app keeps a state record and renders it as a `View` tree. C# decides what is on screen; Flutter only draws it.

A screen mounts control neurons in its view as children, by key. The controls live in the UI module: the neurons in `src/Modules/UI/Controls` and one contract per control (`IToggleSwitchControl`, `IChatThreadControl` and the rest) in `src/Modules/UI/Contracts`, which is what apps and components mount, as in `Child<IToggleSwitchControl, ToggleSwitchProps>(key, props)`. Every action a person takes is a command on `POST /brains/{id}/act`, and a child's view is read from `GET /brains/{id}/apps/{name}/children/{path}`, both through `AppUiEndpoints`. `IScreenTargetResolver` names the screen that takes the command: a compiled app's screen, an agent app's, a sandboxed app's view neuron (`ViewNeuron`, which turns a command its view sends into the app's request), or a synapse unit. A button or field sends a typed signal as its command (`ButtonBuilder.Sends`, `FieldBuilder.Sends`) and the screen's `[On]` reaction for that signal handles it; no view names a C# method, and a control with no action of its own sends `UiInert`, which every screen ignores. The client sends the pressed node's own command; a node's client-local intent (copy, open a window) is performed by the client and never reaches the server. A field's text stays in the client until the field's command carries it as `value`; a live field (`FieldBuilder.SendsOnChange`) sends its command after each pause in typing, and the screen keeps the text in its state. No neuron stores a field. A person's confirmation answer is not a UI event: it goes to `POST /brains/{id}/confirmations/{planId}` (`ConfirmationEndpoints`), the one way to answer one: only a person calling directly answers, and the screens surface and the MCP screen tools read pending confirmations but answer none. The shell's embedded browser reports its connection to `POST /brains/{id}/browsers/{connect|disconnect|unavailable}` (`WebBrowserEndpoints`). The shipped UI Gallery (`GalleryApp`) shows every control and data node, and its scenarios run on the kernel, Flutter and browser drivers.

`ShippedShellAppsModule` (id `os-apps`) carries these neurons into the kernel. When a brain is created, `OsDefaults` installs the default apps into it. `src/IntoChat.OS.Apps/Units` holds the unit sources the product ships; `ShippedUnits` deploys them like any unit made at run time.

### Creator

`CreatorApp` (`src/IntoChat.OS.Apps/Creator`) is the place to make units and watch them run. It shows the brain as a graph, with an inspector for the selected node, edge or trace. It reads everything from the kernel. Its operations are signals:

- `CreatorMake` passes a goal to `IStudio`, which starts a build.
- `CreatorChange` starts a build flow over a unit's current files through `IFlows`.
- `CreatorScenario` runs a unit's kept scenarios and shows the transcript.
- `CreatorSeed` deploys a shipped unit through `ISynapseStudio`.
- `CreatorApprove` and `CreatorReject` resolve a pending approval through `IConfirmationInbox`.
- `CreatorSelect`, `CreatorTrace` and `CreatorReplay` drive the inspector and step through a trace.
- `CreatorShare` publishes the selected unit to your profile.

## Modules and components

A module adds neurons, contracts and settings to the kernel. Each lives in a folder under `src/Modules`. A component, in `src/Components/<Name>`, is the same plus the app screens of that capability. Their layers, from the bottom: the contracts assembly (`IntoChat.<Name>.Contracts`), which other projects reference; the implementation (`IntoChat.<Name>`), which the Kernel references to compose it (the AppHost project references it too, and compiles the component's `Hosting` folder; the test projects reference it as well); the host layer `src/IntoChat.OS.Host`, which a component uses and which references no component today. A component's implementation project references other modules and components only through their `Contracts` projects (`ComponentFacts`). See [modules](modules.md).

Direction: modules and system apps are being merged into components one at a time, and the two roots, `src/Modules` and `src/Components`, coexist until the last one has moved.

## Shell

`ui` is the Flutter client. `ui/lib/desktop` holds the desktop and window frame, `ui/lib/workspace` the app surfaces, and `ui/lib/src/core` the transport to the kernel.

`src/IntoChat.OS.Desktop` is the launcher for one machine. It starts the kernel and the Flutter shell, and keeps its files under `~/.intochat`.

## How a request flows

1. **Shell.** You act in a window. `NeuronChannel` (`ui/lib/src/core/neuron_channel.dart`) sends a call over gRPC, or gRPC-Web in a browser. The call names a brain, a contract, a key, a method and JSON arguments.
2. **Kernel edge.** `NeuronsGrpcService` receives it. `BrainCall` checks that the caller may enter that brain, then `EdgeAuthority` builds the `Caller` (an `Actor` plus brain, conversation, via and inside) and enters it for the call. Only `EdgeAuthority` factories build a `Caller`; the kernel is entered only through `EdgeAuthority.EnterKernel` (in the OS, `PlatformCall.AsKernel`). Reminders, timers and activations, and the work they defer, run as `Actor.Scheduler` of the brain.
3. **Neuron surface.** `NeuronSurface` (`framework/src/DigitalBrain.Runtime.Http/Surface/NeuronSurface.cs`) finds the contract, uses `NeuronBinder` to bind named or positional JSON arguments to the target method, and calls the neuron.
4. **Neuron.** The neuron runs in the Orleans silo. It may change its state and publish signals. `SiloAccessCallFilter` is the enforcement point for who may call what: it reads the caller from `ICallerAmbient`, refuses a call with no caller on every host, refuses a call into another brain, then asks each `ICallFilterStage` in order. That covers neuron contract calls. Every other grain method (a neuron's state inspection, the kernel's and the identity module's own grains) is refused without a caller. Before any of that, an OS silo has no external callers: a grain call the silo process did not send itself (`SiloOrigin`) is refused, whatever caller it states and whichever port it arrives on, neuron contracts included. No product host is an Orleans cluster client: the command-line host calls the edge (`Neurons.Call` over gRPC-Web, or HTTP) with the person's proof and asks to act as the app `cli` (`ActingApp`). A silo opens no Orleans gateway listener unless a gateway port is configured (`TopologyContext.NoGateway`); the local, Desktop, AppHost and Azure topologies configure none, the AppHost strips the gateway endpoint the Orleans resource reference adds, and the Azure install publishes no port beside the HTTP ingress (`InstallPlan`). Because `SiloOrigin` is an object of one process, the rule holds for a cluster of one silo: `SingleSiloGuard` makes a silo that runs `SiloAccessCallFilter` refuse to become active while another live silo is in its cluster, with an error that names the reason, so every OS host needs its own Orleans cluster id and membership.

   The cloud host is a separate Orleans cluster with its own storage namespace (`InstallPlan` gives the Cloud app its own cluster id, service id, grain-state and lease containers and `Home`). It reaches an OS install only over the install's HTTP edge, as a trusted issuer (`IntoChatOS:Auth:TrustedIssuers`): a person signs in with an external sign-in ticket, a visitor tries the install as a guest with a `GuestTicket`, and the cloud relay calls the device enrollment edge (`EnrollmentEdge`) with a `ServiceAssertion` that `IServiceAssertions` verifies and spends once. Nothing on that edge takes an identity from the request: the assertion admits one operation, and the edge acts as the module that owns it. Device chat goes the other way: the install asks the cloud relay over HTTP with the machine credential its device link holds (`IDeviceChatRoute`).
5. **Back.** The result returns as JSON in the reply. The shell also holds a `Watch` stream on the neurons it shows. A change signal tells the view to read again, and Flutter draws the new `View`.

The same `NeuronSurface` serves two other callers. The MCP tools in `src/IntoChat.OS.Kernel/Mcp/Tools` use it, and so does Ino; see [Ino and memory](ino-and-memory.md).
